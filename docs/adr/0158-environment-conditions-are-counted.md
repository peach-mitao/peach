# ADR-0158 环境条件只计数，不发定位事件

- 状态为已采纳
- 日期为 2026-11-12
- 关联 ADR-0110、ADR-0132 与 ADR-0157

## 背景

技术诊断原来只区分两类：代码缺陷上传定位事件并计数，其余情况整条留在本机。盘掉线、媒体缺失或损坏、磁盘满、媒体工具超时、数据库忙这类环境条件也被整条丢弃，维护者看不到它们在各平台、各部署方式下有多常见，也就无法判断产品要不要兜底。

同一套筛选还有两处漏计：一天内第 21 个起的新诊断键整条丢弃，计数日志只带异常类型，对不上代码位置。

## 决策

### 三类处理

| 发生的事 | 处理 |
| --- | --- |
| 代码缺陷 | 每实例每版本上传一条定位事件，全部发生次数进计数日志 |
| 环境条件 | 只计数，带固定的 `condition` 类别和代码位置，不上传定位事件 |
| 用户操作与正常控制流 | 不发送，也不计数 |

`condition` 的取值固定为 `sqlite_io`、`sqlite_busy`、`disk_full`、`io_error`、`media_volume`、`missing_media`、`permission_denied`、`invalid_media`、`timeout`。数据库条件按 `sqlite_errorname` 前缀判定，其余只在媒体环节判定，判据沿用原来留在本机的规则。计数样本只有系统、Python、架构、环节、类别，以及被捕获异常的类型和最内层 Peach 栈帧，不带错误码、路径或原文。

取消、断连、暂停、互斥与文件锁等待超时、不支持的选择器、4xx、低于 error 的日志仍然不发送。来源冷却与失败、元数据提供方故障、httpx 超时、浏览器与验证页不可用、路由主动返回的 502、503、504 本次不纳入计数，继续留在本机；它们会带上来源维度，另行决定。

### 聚合

环境条件先在进程内按诊断键累计，60 秒定时检查或正常退出时并入 `state/remote-reporting-frequency.json`，掉盘时不会每次发生都写一次文件。只计数的行带 `count_only` 标记，补传首次事件时跳过，不占每天 20 个新诊断键的名额。

故障的新诊断键超出当天 20 个时，改用与环境条件相同的粗样本登记为只计数的行，次数照常进计数日志；次日该故障的完整样本可以重新登记并上传定位事件。只计数的新键每天最多登记 100 个，进程内累计也以 100 个键为限，超出部分不再计数。

### 计数日志

计数日志增加 `code_location`（`文件:函数`）和 `code_line`，取被捕获异常里最内层的 Peach 栈帧；没有 Peach 栈帧时不带。环境条件的计数日志另带 `condition`。

## 影响

- 同意说明里的「故障类型、代码位置与发生次数」已覆盖环境条件计数，不新增数据类别，不需要重新同意；`FIELDS["errors"]` 补一句环境条件只统计类别、代码位置与次数。
- 强制退出会丢失进程内尚未并入的累计，与计数日志原有的尽力交付口径一致。
- 接收端按 `condition` 分组对 `occurrence_count` 求和，即可得到各类环境条件的发生次数。
