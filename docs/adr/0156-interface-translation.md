# ADR-0156：界面翻译以 zh-CN 语言资源为源，术语表与门槛放在仓库里

- 状态：已采纳，分阶段实施；第一阶段随本 ADR 合入，第三阶段的①信封与接入点（PR #544）于 2026-11-09、②显示表与③a 任务中心说明句（PR #600、#603）于 2026-11-12 合入；第四阶段于 2026-11-12 开放 Weblate
- 日期：2026-11-08
- 修订：[ADR-0159](0159-interface-text-lives-only-in-locale-resources.md) 把语言资源搬到 `resources/locales/`，后端不再写中文原文、日志改用英文、命令行跟系统语言；第一、三、七条以 ADR-0159 为准。
- 关系：[ADR-0153](0153-content-translations-live-beside-originals.md) 管内容翻译和翻译平台的备选顺序，本 ADR 管界面文案；沿用 [ADR-0022](0022-frontend-vite-preact-strangler.md) 的前端产物入库与 [ADR-0031](0031-frontend-react-boardui-tailwind.md) 的 React 迁移边界。需求来自 issue #398。

## 背景

Peach 的界面只有中文。前端源码里写死的中文文案节点约 7,000 处，分布在 335 个文件；后端还有约 5,500 条会显示给用户的字符串，散在接口报错、任务名、诊断说明和托盘里。

翻译开工前已经按真实页面和实测宽度定好了英文术语：166 个中文词各有一个定稿写法，92 个被否掉的写法标为禁用。页面上能看到的 849 条文案也有了英文草稿。剩下要定的是工程问题：

- 文案放在哪里，键怎么起。
- 界面语言怎么选、存在哪里。
- 后端文案走哪条路。
- 怎么防止新功能继续写死中文。
- 术语以后怎么改、新词谁来定。
- Weblate 怎么接进来。

## 决策

### 一、源文和资源文件

- 源语言是 `zh-CN`。文案放在 `frontend/src/locales/<语言>/<命名空间>.json`，格式是 i18next JSON v4，复数用 `_one`／`_other` 后缀。
- 命名空间按页面组划分，一个命名空间对应 Weblate 的一个组件：`navigation`（侧栏、管理菜单与分区名）、`shell`（全站外壳、通用组件、登录与初始设置）、`settings`（设置面板与配置页）、`cleanup`（数据管理）、`manage`（任务、复核、诊断、采集、统计与口味）、`follow`（关注）、`catalog`（作品、目录、人物、JAV、播放器）、`onboarding`（新手引导与教程）。
- 键是稳定的语义 ID，写成 `区域.对象.用途`，例如 `sidebar.home`。键不含中文，按功能小节和含义起名（如 `organize.rollbackLastBatch`），写进资源后固定，改措辞不换键。几处通用的短词放在本命名空间的 `shared` 小节。
  - 中文只改措辞、意思没变：键不变，Weblate 会把各语言译文标成「需要修改」。
  - 意思变了：换一个新键，旧译文不会被套到新意思上。
  - 同一个中文在不同位置意思不同（「播放」是按钮还是分区名，「版本」是应用版本还是作品版本，「镜像」是镜像站还是安装镜像）：拆成不同的键。
- 英文和 `zh-CN` 由同一个 PR 维护：加文案的人按术语表起草英文，键必须一一对应。其他语言经 Weblate 回流，允许缺键；缺的键显示 `zh-CN`。

### 二、运行时

- 只用 i18next 核心库，不引入 `react-i18next`。整页只有一份实例，在模块求值时从本地偏好缓存同步读出界面语言，用 `t('命名空间:键')` 取文案。遗留 JS、React 组件和启动骨架共用这一份 `t`。
- 换语言就整页重载，不做运行中切换。这样导航词表这类在模块顶层取文案的代码不用改成响应式。
- 资源在构建时打进主包。全部抽完后两种语言共约 520 KB（gzip 约 150 KB），主包从 3.0 MB 涨到 3.6 MB，登录与初始设置页的包从 2.5 MB 涨到 3.1 MB。加第三种语言时改成按语言拆分动态载入，入口不变。
- `<html lang>` 跟着界面语言走。
- 界面语言存在共享设置的 `interfaceLanguage` 里，和「女优名称」一样跟着数据库走，所有设备读同一份。可选值是 `auto` 和已登记上线的语言，后端只放行这些；每种登记的语言都要有资源目录，资源目录可以多于登记的语言（见第六条「新语言」）。
- 默认值是 `auto`，由每个浏览器自己算：按浏览器的语言偏好（`navigator.languages`）找第一个有译文的语言，中文的各种写法都算简体中文；浏览器里一个都没有时，用运行 Peach 的电脑的系统语言（`/api/settings` 的 `systemLanguage`，前端缓存在本地）；再没有就用英文。服务端要用界面语言 L（ADR-0153）时，`auto` 按系统语言算。
- 语言名称用各自语言的自称（简体中文、English），不随界面语言翻译。
- 句中带链接或强调的文案，按整句写成几条键，在组件里组合，保证每种语言能各自调整语序；不引入 `react-i18next`。
- 列表连接和句中引号随语言变：用 `joinList()` 和 `quoted()`（`frontend/src/i18n/index.ts`），不要在代码里写「、」和「」。
- 用来查找或比较的值不用显示文字：设置分区用地址里的 id（`sectionId()`／`sectionTitle()`），和服务端返回值比较的中文、写进地址或请求体的协议值原样保留，标上豁免注释（见第五条）。

### 三、后端界面文案

- 接口返回的一句界面文字旁边加两个字段：`message_code` 是稳定的语义 ID，`message_params` 是插值参数。现有的中文 `message`（成功）或 `error`（失败）留在同一层，没有译文时显示它。成功和失败共用这两个字段名。不用 `code`，因为响应里的 `code` 已普遍表示番号。
- 前端按 `server:<message_code>` 翻译，先用 `exists()` 确认有这条译文，没有就显示服务端原文。i18next 缺键时返回键名，不能拿 `t()` 的返回值判断有没有译文。解析服务端文字的函数只有一个（`frontend/src/core/server-text.ts`），`apiGet`、`apiSend` 和遗留层的 `api()` 都走它。
- 后端给人看的错误抛 `peach.user_messages.UserFacingError`，带 `code` 和 `params`，由 `api.py` 统一转成响应。路由和领域异常按域分批迁移，没迁移的异常照旧透出原文。
- 显示表（下载失败类别、修复与迁移各项、安装方式等）已有稳定英文 id 的，响应带上 id，前端按 `server:<表>.<id>` 取文案，中文名称留作回落。前端不再拿服务端的中文做比较。
- 会落库的文字（任务名、进度、跳过原因）给运行表加可空列，存 code 和 JSON 参数。旧行不回填，显示时回落到原来存的中文；这些表只留最近的运行记录，旧行会自然淘汰。列在改到对应的表时再加，不提前建。`task_run` 一行有两句：进度说明存 `progress_code`／`progress_params`，结束原因存 `error_code`／`error_params`，接口按同名字段下发。句中的任务名和触发方式不进参数，前端按 `task_key` 与 `trigger` 换成当前语言的名字。
- 浏览器之外的界面（托盘菜单与通知）用一个小函数读同一份语言资源，按 `interfaceLanguage` 取文案。
- 命令行输出和日志面向开发者，保持中文，不翻译。
- 这一条在第三阶段分批实施，顺序见第七条。

### 四、术语表

术语表只有一份：`resources/locales/glossary/en.tbx`，Weblate 的术语组件读的也是这个文件。TBX 字段按 Weblate 的映射写：

| 内容 | TBX 写法 |
| --- | --- |
| 中文词 | `langSet xml:lang="zh-Hans"` 里的 `term`（Weblate 的简体中文代码是 `zh_Hans`，写 `zh-CN` 对不上，中文词会读成空） |
| 定义 | `termEntry` 下的 `descrip` |
| 英文定稿 | `langSet xml:lang="en"` 里的 `term` |
| 理由与按位置的用法 | `note from="translator"` |
| 被否掉的写法 | 单独一条，`termNote type="administrativeStatus"` 写 `forbidden` |
| 补进每门语言 | 定稿的条目在 `termEntry` 上写 `weblate-flags="terminology"`；禁用写法只针对英文，不写 |

谁来定：

| 情况 | 谁提 | 谁定 | 怎么落地 |
| --- | --- | --- | --- |
| 新功能加了文案 | 改代码的人 | 不用单独定 | 同一个 PR 写 `zh-CN` 和英文，英文按术语表 |
| 出现新概念（新的导航项、分区名、对象） | 改代码的人 | 维护者 | PR 给术语表加一条，维护者定稿后才合入 |
| 改一个已定稿的术语 | 任何人 | 只有维护者 | 写明理由；同一个 PR 改掉所有含旧写法的英文，旧写法转成禁用 |
| 译者觉得某个术语不好 | 译者 | 维护者 | 在 Weblate 术语表提建议或讨论，同意后按上一行处理 |

英文写作规则：

- 美式拼写：Canceled、color、organize。
- 按钮、标签、菜单只有首词大写；专有名词照原样（Peach、JavDB、CloudDrive）。
- 设置分区、导航和工具卡片的名称用一个词为主，一个词会误导时才写 A & B。
- 按钮、标签、徽标和列名不加句号，完整的说明句加句号；英文里不出现全角标点。
- 量词（部、位、个、张）交给复数规则，不直译。
- 界面翻译不改作品标题、人名、厂牌名、标签值和路径，这些按 ADR-0153 处理。
- 超框按控件类型处理：按钮、导航、标签页、徽标、列名必须落在实测宽度内，放不下先精简措辞，再考虑只留图标；说明、确认、错误这类句子完整表达，由布局负责换行。
- 「本机」= This device。如果句子指的是运行 Peach 的那台电脑，而页面可能在手机上打开（监听范围、只读端、本机路径），中英文都改写成「运行 Peach 的电脑」/ the computer running Peach。

### 五、门槛

| 门槛 | 拦什么 | 位置 |
| --- | --- | --- |
| 前端不写死中文 | `frontend/src` 里带汉字或中文全角标点（、。：；（）「」等）的字符串、模板和 JSX 文字，同一行或上一行没有写明理由的 `i18n-exempt` 注释 | `frontend/test/i18n.test.ts`，计数在 `frontend/scripts/i18n-literals.ts` |
| 日期按界面语言 | 日期和时间格式化不传区域、按浏览器语言出格式 | `frontend/test/i18n.test.ts` |
| 资源一致 | 英文和 `zh-CN` 的键不一一对应；插值占位不一致；入口没登记某个命名空间 | 同上 |
| 禁用写法 | 中文含某个术语时，英文用了它的禁用写法 | 同上，读 TBX |
| 语言白名单 | 后端放行的语言和资源目录不一致 | `tests/test_web_settings.py` |
| 原位改字 | 抽走的文案改不了，或者改到了译文文件 | `tests/test_dev_copy.py` |
| 后端中文只减不增 | 路由模块（`api.py`、`routes_*.py`、`web_*.py`）里的中文和各模块 `raise` 的中文消息，没带 `message_code` 的条数超过逐文件基线 | `tests/test_user_messages.py`，计数在 `scripts/check_backend_copy.py`，基线 `scripts/backend-copy-baseline.json` |
| 后端 code 有译文 | 后端写死的 `message_code` 在 `server` 命名空间的中文或英文里缺键；显示表的中文和 `zh-CN` 资源不一致 | 同上 |

豁免只给不是界面文案的中文：和服务端返回值比较的词、地址参数和请求体里的协议值、站点名这类内容。写法是 `// i18n-exempt: 理由`，理由必写，评审时逐条看。注释、`console` 调用、对象键和导入路径不计数。

以下两项不进每个 PR 的 CI：

- `npm run i18n:terms` 列出还没进术语表的高频中文片段，供维护者定期挑新概念。
- 超框实测：把英文换进真实页面、逐个控件量宽度，比较耗时，在第四阶段放进仓库，作为发版检查手动运行。

原位改字（`src/peach/dev_copy.py`）把 `frontend/src/locales/zh-CN/*.json` 纳入可改范围。抽走的文案在页面上照样能点中修改，改的是源文；英文等译文不在可改范围内。带 `{{名字}}` 占位的值按页面上显示的整句反查，编辑时占位写成 `{名字}`，保存时必须原样保留。

### 六、Weblate

- 平台按 ADR-0153 第七条的顺序选，现用 Hosted Weblate 的 [Peach 项目](https://hosted.weblate.org/projects/peach/)。
- 每个命名空间建一个组件：单语 i18next JSON v4，模板是 `resources/locales/zh-CN/<命名空间>.json`，文件掩码是 `resources/locales/*/<命名空间>.json`，各组件共用 `navigation` 组件的仓库副本。新增命名空间不用手动建组件：`navigation` 装了「组件发现」插件，按 `resources/locales/(?P<language>[^/.]+)/(?P<component>[^/]+)\.json` 匹配，拉到含新文件的提交时照上述设置自动建组件，不删除组件；新组件源文字的「AI draft」标签仍要手动打。新语言的目录名用 BCP 写法（`ja`、`pt-BR`、`zh-Hant`）。写回的 JSON 缩进 2 个空格、不排序键，与仓库一致。
- 开发工具的文字（`scripts/locales/<语言>/dev.json`，ADR-0159 第三条）是单独一个组件，模板是 `scripts/locales/zh-CN/dev.json`、文件掩码是 `scripts/locales/*/dev.json`，其余设置同上；组件发现插件只认 `resources/locales/`，不会自动建这个组件，要手动建。
- 术语组件用 TBX，文件掩码是 `resources/locales/glossary/*.tbx`。Weblate 建项目时自带的本地术语表已删除，术语只有仓库这一份。
- 双语 TBX 没有新语言的模板，Weblate 新开语言时只建一个空的 `<语言>.tbx`，术语组件的进度又只按有条目的语言算，结果空表显示成 100%。所以定稿术语都带 `terminology` 标记，由 Weblate 的术语同步补进每门语言、译文留空，以后新开的语言也一样。同步要求术语组件开着「管理字符串」，只对这一个组件开。
- 同步补进来的条目会被 Weblate 设成只读：它照搬源字符串的只读状态，而双语术语表的源字符串一律只读。这个状态只记在 Weblate 的数据库里，文件里的条目是待翻译的。所以每次新开语言或新增术语后，都要核对该语言术语表是「未翻译」；如果是只读，由管理员在术语组件的「操作 → 仓库维护」里点「重新扫描」，Weblate 会按文件把状态改回来。
- 仓库到 Weblate：仓库的推送 webhook 指向 `https://hosted.weblate.org/hooks/github/`，master 一有提交就拉取。新增的键出现为待翻译；中文改了措辞而键不变，各语言译文标成「需要修改」；删掉的键由「清理翻译文件」插件从各语言文件里一并删掉。组件关闭「管理字符串」，键只在仓库增删。
- Weblate 到仓库：版本控制选「GitHub 拉取请求」，Weblate 的机器人从自己的分叉开 PR，不需要仓库写权限。「挤压 Git 提交」按作者合并，每位译者保留自己署名的提交，合入后计入 GitHub 贡献者。
- 组件带 `i18next-interpolation` 标记，插值检查设为强制，占位不对的译文存不进去。仓库测试另外检查其他语言不多出源文没有的占位。
- 开启建议和投票，不开自动采纳；开启审核，由审核者批准。提交筛选保持「提交所有译文」：还没批准的译文照样写回仓库，不会因为开启审核从文件里消失。
- 英文以仓库为准：PR 作者维护，Weblate 上的英文修改同样经 PR 回来。现有英文由智能体起草，在 Weblate 上带「AI draft」标签，贡献者可以筛出来复核、提建议和投票。
- 新语言：在 Weblate 上开新语言只新建资源目录，不进界面语言的选项。翻到能用后，由维护者在前端 `INTERFACE_LANGUAGES` 和后端 `web_settings.INTERFACE_LANGUAGES` 两处登记；登记第三种语言时，按第二条改成按语言拆分动态载入。
- 第一版不用 `max-length` 标记，超框由实测判断；截图在第四阶段接入。

### 七、分阶段

| 阶段 | 内容 |
| --- | --- |
| 一（本 ADR） | i18next 接入、界面语言设置、`navigation` 与 `settings` 命名空间、术语表、门槛、原位改字 |
| 二 | 前端文案按页面组整份抽取。数据管理组单独一个 PR，其余五组（管理区、关注、设置、作品与目录、全站外壳）与新手引导合成一个 PR 一次抽完，门槛随之收成零。一个文件里的中文一次抽完，不分看得见和看不见；页面上看得见的约 850 条用按定稿术语起草、整页实测过宽度的草稿，其余在同一个 PR 起草，逐条审核交给 Weblate。同时拆开同字异义、改掉拼接出来的半句 |
| 三 | 后端文案改成 `message_code` 加 `message_params`，托盘读语言资源。分六批，见下表 |
| 四 | 开放 Weblate：申请平台、建组件和术语组件、接截图；超框实测脚本进仓库 |

第二阶段合入后，`test/i18n.test.ts` 允许前端写死中文的条数收成零，新代码和老文件一样不能写死中文。后端的界面文字在第三阶段处理：①加上 `scripts/check_backend_copy.py`，按文件统计后端发给界面、还没带 code 的中文字符串条数（路由模块里的全部中文和 `raise` 的中文报错），上限记在 `scripts/backend-copy-baseline.json`，只许减少；之后每批合入时按新的条数把上限调低一次。

| 第三阶段的批次 | 内容 |
| --- | --- |
| ① 信封与接入点 | `UserFacingError` 与响应字段、`server` 命名空间、前端唯一的解析函数、后端基线门槛；HTTP 默认报错和首次访问拒绝带 code；安装方式、修复与迁移两张显示表按 id 翻译 |

## 不采用

- **用中文原文当键**：改一个字，所有语言的译文全部断开；同字异义也没法区分。ADR-0153 的标签组件用中文规范名当键，那是内容词表，和界面文案不同。
- **引入 `react-i18next`**：整页重载切换语言，用不到它的响应式能力；带链接的句子用几条整句键在组件里组合，也不需要 `Trans`。
- **运行中切换语言**：所有在模块顶层取文案的代码都得改成响应式，换来的只是少一次刷新。
- **CSV 术语表**：Weblate 的 CSV 术语导入不带禁用标记。
- **后端按每个请求的语言渲染文案**：落库的文字会混着几种语言，而且要维护前后端两套翻译管线。
- **每个 PR 跑超框实测**：要起样本实例、开浏览器逐页测量，太慢。

## 评审结论

用户 2026-11-07 至 11-08 确认：

1. 先定术语，再看文案；首批只做英文；超框按控件类型处理；英文由智能体按定稿术语起草，PR #443 只作参考。
2. 18 个关键概念定稿。其中四个用户改了写法：目录 = Directory，本机 = This device，喜欢／不合口味 = Like / Dislike，出演者 = Performers。
3. 「本机」采用第四条的写作规则：指运行 Peach 的电脑时改写句子，不靠换术语遮住歧义。
4. 逐条文案交给 Weblate 社区投票和审核者批准，用户只拍板术语；新概念和定稿术语的修改由用户决定。
5. 界面语言默认自动探测：先看浏览器语言，再看系统语言（2026-11-09）。浏览器偏好英文的中文用户会看到英文，可以在设置里固定成简体中文。
6. 第二阶段数据管理组之外的五组页面（管理区、关注、设置、作品与目录、全站外壳）与新手引导在 PR #536 一次抽完，补上「老文件里改中文不受拦」的漏洞；后端文案接着在第三阶段做（2026-11-09）。
7. 后端字段名用 `message_code` 与 `message_params`，不占用表示番号的 `code`；运行表的 code 存在新加的可空列里，旧行不回填（2026-11-09）。
8. 用户建好 Hosted Weblate 项目，要求仓库与 Weblate 双向同步全部接上；现有英文是 AI 初稿，要让贡献者能继续修改、补充和投票（2026-11-12）。
